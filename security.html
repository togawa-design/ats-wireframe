実装方針
Middlewareチェック Next.js の middleware.ts でルートごとに必要ロールを定義。Firebase ID Tokenのカスタムクレームにロールを付与し、リクエストごとに検証。
APIサーバー側チェック フロントエンドの非表示だけでなく、APIエンドポイント側でも必ずロールを検証する。フロントエンドのみでの制御はバイパス可能なため不十分。
職種区分アクセス Staff.position_access（sogo / gino / both）で、スタッフが閲覧できる職種区分を制限。interviewer は自分の担当学生のみ表示（Row-level filtering）。

通信セキュリティ

項目設定内容担当
HTTPS強制 Firebase App Hosting はデフォルトで HTTPS を強制。HTTP へのアクセスは自動リダイレクト。独自ドメインでも TLS 証明書を自動発行・更新。 インフラ 自動
HSTS Strict-Transport-Security: max-age=31536000; includeSubDomains ヘッダーを設定。 BEアプリ
CORS APIルートは自ドメインからのリクエストのみ許可。Access-Control-Allow-Origin にワイルドカード（*）は使用しない。 BEアプリ
CSP Content-Security-Policy ヘッダーで script-src 'self' に限定。インラインスクリプトは nonce 方式を使用。 BEアプリ
セキュリティヘッダー X-Frame-Options: DENY（クリックジャッキング防止）、X-Content-Type-Options: nosniff、Referrer-Policy: strict-origin BEアプリ

入力バリデーション・出力エスケープ

脅威対策
SQLインジェクション Prisma ORM を使用。すべてのDBクエリはパラメータ化クエリで実行（生SQL使用禁止）。$queryRaw が必要な場合は Prisma.sql テンプレートリテラルを使用し、文字列連結でのSQL構築を禁止。
XSS React JSX はデフォルトでHTMLエスケープ。dangerouslySetInnerHTML の使用を禁止（ESLint ルールで強制）。ユーザー入力を含むメール・LINE本文は送信前にサニタイズ（DOMPurifyまたはサーバー側サニタイズ）。
ファイルアップロード 許可拡張子: .pdf / .jpg / .jpeg / .png のみ。
MIMEタイプ検証: Content-Type ヘッダーではなく、ファイルのマジックバイトで検証。
最大サイズ: 10MB（PDF）/ 5MB（画像）。
Firebase Storage Rules で認証済みユーザーのみアップロード可。
保存パス: /resumes/{applicant_id}/{timestamp}_{filename}（予測困難なパスに保存）。
CSRF Next.js の API Routes は Same-Origin の Cookie を使用しないため CSRF リスクは低い。Authorization ヘッダー（Bearer Token）方式で認証しており、CSRF トークン不要。
オープンリダイレクト ログイン後のリダイレクト先は自ドメインに限定。外部URLへのリダイレクトを禁止する allowlist を設定。

検知条件対応アクション

Firebase Security Rules（Storage）

rules_version = '2';
service firebase.storage {
  match /b/{bucket}/o {
    // 履歴書・添付ファイル: 認証済みスタッフのみ読み書き可
    match /resumes/{applicantId}/{fileName} {
      allow read:  if request.auth != null;
      allow write: if request.auth != null
                   && request.resource.size < 10 * 1024 * 1024   // 10MB上限
                   && request.resource.contentType.matches('application/pdf|image/.*');
      allow delete: if request.auth.token.role == 'admin'
                    || request.auth.token.role == 'recruiter';
    }
    // それ以外は全拒否
    match /{allPaths=**} {
      allow read, write: if false;
    }
  }
}

Cloud SQL セキュリティ設定

設定項目設定内容
ネットワーク Public IP を無効化。Firebase App Hosting からは Cloud SQL Auth Proxy（Private IP） 経由でのみ接続。インターネットからの直接接続は不可。

アカウント管理運用ルール

シナリオ手順
スタッフ入社時 admin が Staff テーブルに登録 → Firebase Auth でアカウント作成 → 最小権限のロール（recruiter または interviewer）を付与。初回ログイン時に Google OAuth 経由で認証確立。
スタッフ退職時 即日: Firebase Auth でアカウント無効化（disabled: true）→ Staff.is_active を false に更新。期限切れセッションの強制失効（Firebase Auth リボーク）。AuditLog は保持。
portal_token 漏洩疑い admin が AgencyContact のトークンを即時再発行。旧トークンは token_invalidated_at を設定して無効化。エージェントに新しいURLを再送付。
パスワードリセット Google OAuth 認証のため ATS 側にパスワードは存在しない。Googleアカウントのセキュリティ問題は先方の IT 管理者が対応。

インシデント対応フロー

⚠️ 個人情報保護法（改正2022年施行）により、1,000件以上または要配慮個人情報の漏洩は個人情報保護委員会への報告（72時間以内）と本人への通知が義務。ATS は6,700件以上のPIIを保持するため、漏洩時は必ずこのフローを実行する。
フェーズ時間軸アクション担当
① 検知・初動 発生〜1時間 漏洩・不正アクセスの疑いを検知した担当者は即座に開発担当（卓也さん）に連絡。
該当するAPIエンドポイント・アカウントを暫定的に無効化またはレートリミット強化。
AuditLog からアクセス履歴を取得・保全（証拠保全）。 		検知者 + 開発
② 影響範囲特定 〜6時間 漏洩したデータの件数・内容・期間を特定（AuditLog / Cloud SQL ログを調査）。
影響を受けた応募者のIDリストを作成。
攻撃経路を特定し、脆弱性を閉塞。 		開発担当
③ 報告（社内） 〜12時間 先方（クライアント）の個人情報保護責任者（通常は情報システム部長または法務部）に報告。
報告内容: 発生日時・影響件数・影響を受けたデータ種別・暫定対策・今後の対応方針。 		開発 + クライアント
④ 法的報告 72時間以内 個人情報保護委員会への報告（1,000件以上の漏洩または要配慮個人情報含む場合）。
報告フォーム: https://www.ppc.go.jp/
本人（応募者）への通知: 漏洩した個人情報の内容・対応状況・問い合わせ窓口を通知。 		クライアント（法務）
⑤ 根本対策・再発防止 〜1週間 脆弱性の根本修正・デプロイ。
セキュリティレビュー実施。
インシデントレポート作成（原因・影響・対策・再発防止策）。
必要に応じて外部セキュリティ診断を実施。 		開発担当
